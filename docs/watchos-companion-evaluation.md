# watchOS 配套 App 评估（M3）

| 项 | 内容 |
| --- | --- |
| 议题 | 是否需要 watchOS 配套 App 作为「手表在身边」的信号源 |
| 结论 | **本期不实现**；继续以「多证据 BLE 识别 + 手动绑定 + 距离校准」为主路径，配套 App 作为兜底方案保留到 M4 之后再评估 |
| 评估日期 | 2026-10-15（2026-10-15 补充调研后修订，见 §6） |
| 关联风险 | R-02（Apple Watch 广播内容与可见性随 watchOS 变化） |
| 相关文档 | `docs/anti-false-lock-research.md`（误锁问题调研依据） |

---

## 1. 问题背景

Mac 端通过 `CBCentralManager` 扫描周边 BLE 广播，再用「名称 / 厂商数据 / 服务 UUID / 已绑定 ID」四条证据识别手表（FR-02）。该方案在以下情况会失效：

1. 手表已与 iPhone 建立连接时，广播内容与频率受系统策略限制，设备名可能不可见；
2. 部分 watchOS 版本在后台不广播自定义的连续性服务 UUID；
3. 用户手表没电 / 关机时，本就无法区分「真离开」与「无广播」（已通过 `FarReason.signalLost` 在 UI 上区分）。

表现为「设置 → 设备」候选列表长时间为空，用户无法完成绑定。

## 2. 备选方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| A. watchOS 配套 App 主动广播 | 手表端用 `CBPeripheralManager` 以固定 service UUID 持续广播 | Mac 端识别确定性最高，可摆脱系统广播策略 | 广播持续性与 watchOS 后台策略强相关（前台可保，后台无保证）；需额外签名/公证与分发；手表耗电增加 | 兜底方案，暂缓 |
| B. iOS 中转 App | iPhone 读手表状态并上报给 Mac | 可靠性高；**Near Lock / Unlox（原 MacID）等同类产品走的正是这条路** | 需要常驻 iOS App，违背「不依赖手机中转」的产品目标 | 不做（但它是业界常态，本项目属有意取舍） |
| C. 复用系统 Continuity 状态 / Apple 官方自动解锁 | 用系统「使用 Apple Watch 解锁」 | 零识别成本、Apple 官方实现，可靠性最高 | 依赖同一 Apple 账户 + 双重认证 + 手表已佩戴且设密码；**无第三方 API**，且只解决「解锁」，不解决「离开锁屏」 | 不做为依赖，但**明确为上层方案**（见 ADR-08） |
| D. 维持现状 + 增强诊断 | 多证据识别 + 手动绑定 + 校准向导 + 误锁反馈自动调参 | 零依赖、零上架成本、隐私面最小 | 极端情况下仍可能识别不到 | **本期采用** |

## 6. 调研修订（2026-10-15）

初版中「watchOS 后台广播受限」是**未经查证的表述**，且混淆了"广播"与"连接"：Apple 开发者论坛的一手帖显示，watchOS 在 `HKWorkoutSession` 期间可以长时间维持 BLE **连接**（数小时、息屏亦可）；真正没有保证的是 App 进入后台后的**广播**持续性。修正后的理由为：

1. **成本**：A/B 方案都要引入第二个可执行产物，签名、公证、分发与后续兼容维护成本远高于收益；
2. **收益不确定**：广播持续性受 watchOS 后台策略约束，无法承诺"一定能被扫到"；
3. **已有更好的定位**：Apple 官方「用 Apple Watch 解锁 Mac」已覆盖解锁侧（依赖 iCloud 身份 + Continuity，第三方无法获得），本项目应聚焦它**没有覆盖的"离开即锁屏"**这一侧（ADR-08）；
4. **已有缓解手段**：校准向导、误锁反馈与自动调参、`FarReason` 区分「扫描不到」与「真的离开」，已覆盖"识别不稳定 → 参数不合适"这一类问题。

> 注：macOS 端 `CBCentralManager` 扫描到的 Apple 设备以随机地址 + IRK 形式广播，第三方拿不到 IRK，因此识别只能靠启发式（名称 / 服务 UUID / 厂商数据）。社区逆向（furiousMAC/continuity、PETS 2019 论文）已还原 Continuity 广播线格式，这是未来提升识别准确度的方向，但需真机抓包确认类型值后再落地。

## 3. 选择 D 的理由

1. **成本**：A/B 方案都要引入第二个可执行产物， Developer ID 签名、公证、分发与后续兼容维护成本远高于收益；
2. **收益不确定**：watchOS 后台广播本身受系统节流，无法承诺「一定能被扫到」，投入产出比不确定；
3. **已有缓解手段**：本迭代补齐的校准向导（FR-14）、误锁反馈与自动调参（FR-16）已经覆盖了「识别不稳定 → 参数不合适」这一类问题；`FarReason` 也让「扫描不到」与「真的离开」在日志里可区分。

## 4. 重新评估的触发条件

满足任一条件时重启本评估：

1. 真机验收中出现「候选列表持续为空，且重启蓝牙无效」的案例 ≥ 3 例；
2. watchOS 提供稳定可用的后台 BLE 广播能力（或 Apple 开放手表在场状态的公开 API）；
3. 产品目标变更，允许引入 iPhone 中转（则优先评估方案 B）。

## 5. 若启动方案 A 的架构草案（供未来参考）

```
watchOS App（CBPeripheralManager）
    └─ 以 service UUID <WatchLock 自定义 UUID> 持续广播，payload 含 1 字节版本号
           │  RSSI
           ▼
Mac 端 WatchScanner
    └─ 在 WatchMatcher 中新增证据：命中该 UUID 即入选，并优先作为绑定候选
```

- 心跳与电量：广播间隔建议 ≥ 500 ms，前台 1 s 内发出首帧；
- 兼容：Mac 端必须保持「没有配套 App 也能用」，即该 UUID 只是**新增证据**，不是必要条件；
- 分发：随主 App 以同一 Developer ID 签名，不做独立上架。
