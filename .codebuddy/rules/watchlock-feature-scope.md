# WatchLock 功能扩展准入规则

**原则：对新增功能保持克制。** WatchLock 是一款「离开即锁」的小工具，核心是锁得准、不误锁、不打扰。
功能越多，误锁路径、设置项、权限面、维护成本和本地化文案就越多。**不做，是默认答案**；
只有证明确实值得，才做。

## 1. 先分析、给评估，再动手（硬性）

收到「继续功能扩展」「再加点功能」之类指令，或自己想到新功能时，**不得直接写代码**。流程：

1. **需求分析**：这个功能解决谁的什么问题？不做会怎样？有没有真实依据（用户反馈、实测、已知误锁 / 漏锁案例），
   还是只是「看起来有用」？
2. **输出评估并等用户确认**：用下面第 2 节的模板写给用户，推荐结论明确（做 / 不做 / 缓做），
   **等用户明确同意后才实现**。
3. 用户确认后再按里程碑推进，实现完补单测、跑质量门、同步文档（见第 4 节）。

只有下列情况可以跳过评估直接改：修复缺陷、补齐文档已声明但未兑现的行为、纯重构、
用户已经**明确指定**要做的具体功能（用户的明确指令即视为已确认，但仍应在动手前用一两句话复述范围与取舍）。

## 2. 评估模板

每个候选功能一小段，不超过 8 行：

| 项 | 内容 |
| --- | --- |
| 要解决的问题 | 谁、在什么场景、现在怎么受影响；**依据**是什么（实测 / 反馈 / 推测，推测要写明） |
| 不做的代价 | 用户有没有变通办法（已有设置、系统自带功能、手动操作） |
| 与核心目标的关系 | 是否直接服务「锁得准 / 不误锁 / 不打扰 / 隐私优先」 |
| 成本 | 新增设置项数、权限 / 网络 / 隐私面、对既有锁定路径的影响、测试与文案量 |
| 风险 | 会不会让「该锁没锁」或引入新的误锁路径；能否默认关闭 |
| 结论 | **做 / 不做 / 缓做**，并给一句理由 |

多个候选时先给**排序后的短名单**，并明确哪些建议砍掉，不要把所有想法都摆出来让用户选。

## 3. 准入门槛（逐条过，不满足的默认不做）

- **有真实问题**：有实测数据、用户反馈或明确缺陷支撑；「可能有人想要」不算。
- **没有更简单的替代**：已有设置能否覆盖？系统自带功能（如系统设置、快捷指令）能否解决？能否只调默认值或改文案？
- **不稀释核心**：不能让主流程（扫描 → 判定 → 锁定 / 唤醒）更复杂或更难解释。
- **会改变锁屏行为的，必须默认关闭**，并在界面与文档写明代价（参考 FR-04 §5、FR-19、FR-20、FR-22）。
- **新增设置项要克制**：每加一个开关都要说明为什么不能用合理默认值代替；优先合并 / 收进已有页面，不新增页面。
- **不扩大隐私面**：不新增网络请求、不读取位置 / 摄像头 / 麦克风等额外权限，除非是核心必需且用户明确同意。
- **可验证**：纯逻辑能落单元测试；依赖真机行为的部分要如实标「待验证」，不能当成已完成。
- **维护成本可接受**：不引入常驻后台任务、私有 API 依赖或需要持续跟进系统版本的特性，除非评估里写清楚并经确认。

## 4. 做完之后

- 在 `REQUIREMENTS.md` 登记 FR 编号、依据、默认值与已知限制（延续既有写法，含「未验证」项）。
- 同步帮助手册（`docs/help.md` / `docs/help.en.md`）、本地化译文（`Scripts/localization.py check`）和单测。
- 对**砍掉 / 缓做**的候选也在评估里留一句理由，避免以后重复讨论。

## 5. 反例（不要这样做）

- 收到「继续」就一口气加几个功能、事后才告诉用户。
- 为了让功能列表更丰富而做的开关（没有真实问题、没有数据）。
- 把可以靠默认值解决的事做成设置项。
- 先实现再找理由。
