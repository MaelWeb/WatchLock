# 界面视觉迭代（fork + playground）

方法来源：Railcode 创始人对自家官网的复盘（见 `references/source-notes.md`）。
凡**不出自原文**、为适配本项目而加的内容，一律标注「（项目适配）」。

## 核心立场

- **"有品位"= 你自己喜欢。** 以使用者本人喜不喜欢为准，不追求客观评分。
- **非设计师很难凭空造概念，靠输入。** 看别人的设计 + 让 agent 批量出稿，再组合、反复迭代。
- **起步阶段海量生成，绝大多数不采用**（原文说约 99%），偶尔捞出一个组件或一个新点子。不采用不等于没价值，它们负责打开思路。
- **死路是常态。** 原文：大多数迭代是死路。
- **过程要开心。** 原文的最后一句，也是目标情绪本身（见工作流 7）。

## 何时使用

- 新增/重做界面，或对某个界面的视觉方向做调整
- 产出或更新 `docs/ui-design/` 下的 HTML 设计稿
- 把设计稿落成 `Sources/WatchLock/UI/` 下的 SwiftUI 代码
- 用户说"不好看""再改改""多给几个方案"这类没有明确验收标准的视觉需求（项目适配）

## 工作流

### 1. 找一个具象的出发点（允许被推翻）

从产品本质推出一个**一句话能说清的具象点子**。原文：Railcode = "code on rails"，用户用起来很开心 → rails + fun = 过山车。

这个点子不必一次到位，也不是必须在画第一屏之前就定死：
- 原文里先是单个过山车，放进页面后显得突兀，才长成"整个游乐园"。
- 原文还先让 agent 出过一批"有趣的开发者工具网站"mockup，大多是 slop，但后来 CTA 的灵感恰恰从里面捞出来。

（项目适配示例，非原文）：`"信号在衰减"`、`"手表离开，Mac 自己上锁的距离感"`。

### 2. 广度采样：看 + 批量生成

两种来源，目的是"open my mind"，不是直接交付：

1. 翻网页，收集喜欢的设计
2. 让 agent 一次生成同一事物的**多种风格**

配套做法（均出自原文）：
- **多看，哪怕很烂。** 早期接触大量设计，后面可能捞到宝。
- **持续看。** 常回访喜欢的站点、不断找新的；即使最终没用上具体内容，也影响判断。
- **喜欢的组件直接当底座**，在它上面改。
- **用具体样例引导 agent，而不是形容词。** 原文："clear examples are also the best way to steer coding agents"。给站点链接、截图或已定稿的元素；并记下"参照了谁、借了什么"。

#### 参考站怎么用（项目适配）

站点清单、各站实测可抓取性、搜索词、以及"借什么不借什么"见 `references/inspiration-sources.md`。要点：

- **分层使用，别混着借。** 真实同类 macOS App → 控件形态与克制程度；Apple HIG → 硬约束；
  Dribbble / Behance → 配色与打磨感；Awwwards / Land-book / Godly → 动效与氛围。混用会互相打架。
- **形态听 HIG，取向听灵感站。** Dribbble 类产物多是渲染稿/网页稿，照搬会把原生界面带成 web 风，
  违反 `.codebuddy/rules/watchlock-ui.md` §2.1/§3。
- **抓取只能拿到文字元信息，拿不到图。** Dribbble 与 Pinterest 实测直接被拦。所以：
  需要看图时**请用户提供截图或链接**，不要反复重试抓取，也不要在没看到图的情况下假装参考过。

#### 方向还没定时的做法：出风格探索稿（项目适配）

当用户只有"想要更好看"而没有具体取向时，让 agent 基于母题和参考站意象，**并行出几版差异明显的风格探索稿**，
覆盖不同取向（如：系统原生克制 / 工具感密度 / 强状态色 / 轻插画氛围），再收敛。这与原文的强度谱系同源，
区别是谱系的轴从"复杂程度"换成"设计取向"。

### 3. 强度谱系 + go wild

- **强度谱系**：让 agent 沿「极简 → 复杂/夸张」给出多个版本。整条谱系都不喜欢，多半是选错了谱系（原文用词是 "probably"）；也能借此判断该更克制还是还有空间更疯。
- **go wild**：一个概念至少 4 版，有时 10 版；**至少一半**给出一定指引，其余明确让 agent "go wild"。放任的那批大多很糟，但提供火花——原文里丑陋的霓虹稿把作者从 ASCII 思路带到更有野心的方向。
- 可以让 agent **并行出两版**。原文 prompt 之一："…build two in parallel actually. one of them should have a transparent background"。
- **保留可追溯的记录**：原文作者为复盘把每个原型与生成它的 prompt 建成索引（事后整理的，并说自己喜欢"easily accessible trace of my process"）。

### 4. 单文件原型，满意后才拆组件

设计阶段始终用**一个文件**，满意（并进入文案阶段）后才拆成可由 agent 并行编辑的组件。
原因：这样 fork/复制、改一两处、并排对比最快。

本项目对应（项目适配）：先在 `docs/ui-design/NN-<页面>.html`（配 `mockups.css`）里做完整屏，再落到 `Sources/WatchLock/UI/`。

### 5. fork 对比，永不删 fork

- 觉得"还差点什么"就**复制一份，改一两处，并排对比**。原文即是：已经很满意，给朋友看过，仍觉得哪里不对，才开始 fork。
- 可以在 fork 上继续长，也可以回到原稿，**但不删除任何 fork**。
- （项目适配）`.codebuddy/rules/watchlock-ui.md` §8 规定 `docs/ui-design/` 下每个界面只保留最新一份，禁止 `-v2`/`-new`/日期后缀。因此 fork 与实验稿一律放 `docs/ui-design/.scratch/`（已在 `.gitignore`），并在 `.scratch/INDEX.md` 按 `文件 → 生成 prompt → 结论` 记账。

### 6. playground 调变量

颜色、字体、位置这类要反复试的变量，做成**可实时调节的页面**，而不是走"告诉 agent 改 → 等 → 再看"的慢循环。
原文例子：草地从蓝改绿后仍不是想要的绿 → 建 playground，同时调强调色/文字色/草地色/背景色，找到满意的草地色调。

（项目适配）模板见 `assets/playground.html`，复制到 `docs/ui-design/.scratch/` 使用；细节见 `references/iteration-recipes.md`。

### 7. 收敛期的做法（均出自原文）

- **孤立元素放进页面会突兀 → 扩成语境，而不是删掉。** 单个过山车放进模板里"wtf is a rollercoaster doing here"，于是长成整个公园。新元素也不必独立存在：原文的条带最终成了"到下一区块的颜色过渡"。
- **范围克制。** 作者做出了可玩的迷你游戏，试玩后判断"有点过了"，退回单个过山车。
- **资产以已定稿的元素为锚。** 以过山车的风格为锚做游乐设施，动画逐个手挑、打磨；风格落定后，新图标/资产都参照它——"把 vibe 定下来，才有稳定的方向感"。
- **用目标情绪裁决。** 目标是"fun"，白底没有 fun → 改天蓝加云，"差异巨大"；此后"hero 决定了整个站点的其余部分"。
- **接受自然出现的好选择。** 绿色自然出现，就顺势得到浅绿/深绿区块和"泥土"footer，而不是强行改回产品蓝（代价是产品本身的设计可能要回头调）。
- **静态方案都不对时，考虑随状态变化。** 导航栏试了白/浅蓝/浅绿/深绿四种静态版，最后"全都要"：随当前区块背景色变化。
- **基调先于细节**：草地定了之后才开始"obsessing over details"；细节永远磨不完，但在基调稳定之后。

### 8. 定稿 → 覆盖正稿 → 落成 SwiftUI（项目适配）

1. 选中的方案**覆盖** `docs/ui-design/NN-<页面>.html` 并重新渲染同名 PNG（命令见规则 §8）
2. 确认出图没有被裁切（画布不够就调大 `--window-size`）
3. 落成 SwiftUI 时遵守 `.codebuddy/rules/watchlock-ui.md`：只用 `WLTheme` token、优先复用 `UI/Components/`、不写嵌套滚动、破坏性操作二次确认、补 `.help()`/无障碍
4. playground 里试出来的色值/尺寸同步回 `WLTheme.swift`，保持设计稿与实现单一来源
5. `swift build` + `swift test` 通过；纯逻辑补单元测试

## 本项目注意事项（项目适配）

- **视觉调参在 HTML 里做完再落地。** 仓库目前没有 `#Preview` 惯例，不要为调颜色而在 SwiftUI 里引入预览脚手架。
- **不要污染 `docs/ui-design/`。** 实验稿、fork、playground 全部进 `.scratch/`。
- 生成设计稿时一次要多稿，并优先使用视觉表现更好的模型。（原文是点名厂商的个人经验，这里中性化，见 `references/source-notes.md`。）

## 反模式

| 反模式 | 正确做法 |
| --- | --- |
| 只出一个方案就开始实现 | 一个概念先出 4~10 版，有对比才有判断 |
| 已经满意就收工，哪怕隐约觉得不对 | 觉得不对就 fork 一份改一两处并排看（原文的起点） |
| 用"高级一点""更现代"这类形容词指挥 agent | 给具体参照：站点、截图、已定稿的元素 |
| 从 Dribbble 照搬布局与控件样式到原生界面 | 只借色彩/层次/动效，形态以 Apple 同类应用与 HIG 为准（项目适配） |
| 没看到图就说"参考了某站" | 先取到截图或链接，取不到就说明局限（项目适配） |
| 孤立元素塞进页面就当完成 | 扩成语境，或做成相邻区块的过渡 |
| 做出一个很炫的东西就非要用上 | 判断是否"太过"，敢于退回克制版本 |
| 把 fork 存进 `docs/ui-design/`（项目适配） | 放 `.scratch/` |
| 在 SwiftUI 里逐个参数来回改（项目适配） | 回 HTML playground 调，再一次性落地 |
| 把"不采用"等同于"可以删" | 方案与 prompt 留记录；fork 一律不删 |

## 检查清单

- [ ] 有一个具象的出发点（允许后来被推翻）
- [ ] 一个概念至少 4 版，其中至少一半给了指引、其余是"go wild"
- [ ] 做过「极简 ↔ 夸张」的强度谱系
- [ ] 给 agent 的是具体参照，不是形容词；记下了参照来源
- [ ] 参考按来源分层使用，没有把网页稿的布局/控件形态照搬进原生界面（项目适配）
- [ ] 需要看图时确实拿到了图（用户截图或实际浏览），没有凭空声称参考过（项目适配）
- [ ] 保留了方案及其生成 prompt 的可追溯记录
- [ ] 单文件原型迭代完成，未提前拆组件
- [ ] fork 都在 `.scratch/` 且未删除，`INDEX.md` 已更新（项目适配）
- [ ] 反复试的变量走过 playground，不是靠嘴改
- [ ] 孤立元素已融入语境；风格定下后新资产以它为参照
- [ ] 正稿覆盖同名 HTML/PNG，出图无裁切（项目适配）
- [ ] 落地代码只用 `WLTheme`、复用现有组件；`swift build` + `swift test` 通过（项目适配）
